# 开发指南

## 开发原则

- 后续开发优先遵循项目现有技术栈、目录结构和代码风格；改变基线需要明确理由和用户确认。
- 先确认当前阶段与产品范围，再实现功能。
- 使用最少依赖完成当前需求。
- 不在同一迭代混入无关重构。
- 用户数据与源代码分离。
- 数据结构变化必须有迁移方案。
- 新功能至少验证核心成功路径和失败路径。
- 文件已存在时，在保留有效内容的基础上合并更新；重写前先证明旧内容已失效。

## 需求沉淀

- 讨论中已明确的功能、业务规则和交互细节及时写入 `requirements/` 对应文档。
- PRD 只写已经确认的信息，并为每项可实现需求提供可验证的验收标准。
- 不完整信息进入 `requirements/open-questions.md`，标记提出日期、影响范围和需要谁确认。
- 需求被替换时更新当前 PRD；废弃内容按项目历史隔离规则处理。

## API 同步

- 新增或修改 Route Handler、Server Action 或跨边界数据契约时，先检查 `api/README.md`。
- 接口文档记录输入、输出、错误、权限、幂等性与验证方式。
- 代码、类型、测试和接口文档必须描述同一行为。

## TypeScript 与 Next.js

- 保持 TypeScript `strict`，使用 `@/*` 导入 `src/` 内模块。
- 默认使用 Server Component；需要浏览器状态、事件或 React Flow 时才建立清晰的 Client Component 边界。
- 写 Next.js 代码前读取当前安装版本附带的 `node_modules/next/dist/docs/` 相关文档。
- 避免 `any`；确需使用时在最小边界内说明原因。

## 版本工作流

1. 开始任务前读取 `PROJECT_STATUS.md` 和任务对应文档。
2. 确认工作树状态，避免覆盖未提交变更。
3. 设计实验前创建 Git 检查点或独立分支。
4. 只修改任务范围内的代码和文档。
5. 运行与风险匹配的检查、测试和构建。
6. 接受方案后更新当前文档、状态和必要的变更日志。
7. 放弃实验时恢复实验前检查点；不要把失败方案残留在当前文档。

## 计划书

短任务可在会话内列出计划。跨会话或需要逐项评审的任务，在 [docs/plans](plans/README.md) 维护一份 `<任务名>.md`，从项目状态链接。写明目标、范围、验收标准、预计改动、实施步骤和待更新的记录。涉及结构调整或数据迁移时，补回退点。需要用户决定的范围或架构在实施前确认。

| 变化 | 处理 |
|---|---|
| 目标和验收不变，调整技术或步骤 | 更新原稿，保留已完成项，修正余下步骤与验证。旧版本用 Git 追溯。 |
| 同一目标下，用户行为、数据契约或验收范围改变 | 在原稿说明新旧差异、已做改动去向和风险，确认后实施新的范围。 |
| 原目标取消，或新目标可独立验收 | 结清原任务的已做变更和遗留项，再开新计划。 |

## 任务收尾检查

1. **确定范围。** 对照计划和 Git 基线，核对属于本轮的暂存、未暂存和新增文件。保留其他任务的改动。
2. **核对实现。** 检查已确认需求、模块职责、接口和数据约束。只跑能验证改动影响的检查，记录命令、结果与未验证项。
3. **同步记录。** 按下表更新对应事实。每条规则维护在一个位置，其余入口链接过去。
4. **处理临时材料。** 查旧入口、实验代码、兼容分支、重复测试和生成文件的真实引用与用途。确认回退点并核对有效结论已同步，再移除完成、取消或替换的计划，修正链接。Git 可追溯普通修订；确有独立价值的决策或迁移依据保留在对应专题或隔离历史。有可能影响用户流程或数据的清理，请用户验收受影响路径。
5. **完成报告。** 列出改动、同步的记录、验证、仍待确认的事项和下一步。只审查时按证据报告问题，实施留待单独授权。

| 变化 | 更新位置 |
|---|---|
| 当前阶段、在办任务、阻塞或下一步 | [项目状态](../PROJECT_STATUS.md)，保持为短索引 |
| 已确认的用户行为或验收 | 对应功能 PRD，技术边界和约束写对应设计 |
| 持久化、接口、错误或兼容规则 | 对应数据或 API 文档，连同实现与验证 |
| 模块职责、入口或长期取舍 | 对应架构或文件地图；有长期影响的决定写 ADR |
| 实际改动、验证和未结项 | [当前日志](logs/current.md)；稳定交付时更新 `CHANGELOG.md` |

发起复核可直接说：「按任务收尾检查，对照 [基线提交] 到当前工作区中属于 [任务名] 的差异，列出架构偏差、文档遗漏、应清理项和验证证据。先审查。」更多示例见[提示词指引](../指引.md)。

用户确认完成的文档在核对链接和依据后单独 Git 存档。提交只纳入本次完成的文档，保留工作区其他变更；交付时报告提交号。

## 质量门槛

基础检查使用 `npm run check`，依次运行基础测试（含迁移验证）、视频拆帧测试、AI 测试、视频下载测试、ESLint、路由类型生成及 TypeScript 检查、生产构建。浏览器和其他专项验证按功能另跑。报告写明实际运行的命令和结果。

临时使用 `MOWO_NEXT_DIST_DIR` 时，收尾检查 Next 是否向 `tsconfig.json` 写入了本次生成的类型路径。常用验证入口复用固定输出目录。一次性目录在任务结束后退出共享类型配置，并在清除前核对脚本引用与全新构建结果。

## 新节点外侧操作接入

使用 `NodeQuickToolbar` 并提供稳定的类型编号、类型名称和 `QuickAction[]`。每项操作声明稳定编号、名称、图标、执行动作或下载地址、默认栏目和文字显示方式；通过 visible/disabled/pressed 表达节点状态。运行中状态、任务引用和内部业务按钮保留在功能模块中。未来视频等模块新增操作只需扩充操作清单。

类型编号决定偏好的共享范围。完整清单需包含空节点和有素材节点可能出现的全部操作，状态变化通过 visible 控制。新增操作自动补入默认位置，原有设置继续生效。避免为同一操作的不同状态使用多个编号，例如导入与替换共用 import。设置存储于本机浏览器，不写入画布文档或项目资产。
