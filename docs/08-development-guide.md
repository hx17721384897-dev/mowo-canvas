# 开发指南

## 开发原则

- 先确认当前阶段与产品范围，再实现功能。
- 使用最少依赖完成当前需求。
- 不在同一迭代混入无关重构。
- 用户数据与源代码分离。
- 数据结构变化必须有迁移方案。
- 新功能至少验证核心成功路径和失败路径。

## 版本工作流

1. 开始任务前读取 `PROJECT_STATUS.md` 和任务对应文档。
2. 确认工作树状态，避免覆盖未提交变更。
3. 设计实验前创建 Git 检查点或独立分支。
4. 只修改任务范围内的代码和文档。
5. 运行与风险匹配的检查、测试和构建。
6. 接受方案后更新当前文档、状态和必要的变更日志。
7. 放弃实验时恢复实验前检查点；不要把失败方案残留在当前文档。

## 文档同步

- 当前行为改变：更新对应主题文档。
- 当前阶段改变：更新 `PROJECT_STATUS.md`。
- 稳定版本交付：更新 `CHANGELOG.md`。
- 重要且已接受的方向变化：新增 ADR。
- 普通代码修改不需要制造 ADR。

## 质量门槛

脚手架建立后补充实际命令。预期至少包括类型检查、Lint、单元测试和生产构建。未经运行的检查必须明确说明，不能写成已经通过。
