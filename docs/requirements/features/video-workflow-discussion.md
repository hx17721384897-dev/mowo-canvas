## 2026-11-11：用户提出的目标流程

1. 使用已有或待接入的视频下载能力，获取 B 站等平台的视频素材；下载完成后，素材进入当前项目素材库。
2. 从素材库把视频拖到画布。较短或较小的视频可直接在画布上展示；较长或较大的视频出现是否进入视频编辑的提示。用户选择进入后，打开专门的视频编辑页面。
3. 视频编辑页面自动检测分镜并拆成相应片段。用户会提供一款开源软件作为功能参考；先理解其产品能力，再决定适合 MOWO 的范围。
4. 用户选择片段导入画布，并在画布上继续编辑片段，例如对片段拆帧。

这里的“分镜”暂按视频中的镜头或场景边界理解，尚未确认是否还包括语义段落、台词或人工标记。“小/大视频”的判定标准也尚未确定。

## 与当前项目的衔接

- 现有资产模型已包含视频类型，资产与画布节点分离；下载或导入后先进入资产库，再由用户放入画布。
- 本地视频导入与基础画布播放目前已有实现，详见[本地视频需求](local-video-import.md)。B 站下载的底层能力已验证，正式下载弹窗与任务入库仍待集成。用户最初所说的已完成下载功能位于同级独立项目 line。
- 已有动图拆帧、序列帧编辑及派生资产关系，可作为视频片段继续拆帧时的交互与数据语义参考；视频片段仍需明确独立身份、起止时间和来源关系。

## 待讨论的产品决策

1. **参考软件**：开源软件的名称或仓库链接是什么？重点借鉴其自动分镜、时间线、片段管理、预览或导出中的哪些能力？
2. **下载来源与边界**：B 站下载是否直接纳入本轮 PRD？除 B 站之外的首批平台、登录态、清晰度选择及本地文件导入各要做到什么程度？
3. **画布与编辑页的分流**：用时长、文件大小、分辨率、帧数或设备性能中的哪些指标判断“大视频”？提示是建议还是必须先进入编辑页？
4. **自动分镜结果**：检测依据是画面切换、内容语义，还是两者都要？结果是否允许手动合并、拆分、调整边界和重跑？
5. **片段回到画布**：导入时引用原视频的时间区间，还是生成独立视频文件？片段节点需要哪些就地操作；拆帧是抽取全部帧、按间隔抽帧，还是由用户选定关键帧？
6. **编辑页范围**：第一版只做分镜检测与片段选择，还是同时包含时间线剪辑、字幕、音频、转码和导出？

## 2026-11-11：下载功能优先讨论

用户明确首个讨论和设计主题为视频下载。现有参考有两处：

- 本地 `line` 工具（Python/Flask）已支持应用内 B 站扫码、单视频或指定分 P 链接、`b23.tv` 短链、异步任务进度，使用 `yt-dlp` 获取当前账号可用的最高格式并由 FFmpeg 合并音视频。其登录凭据只保留在进程内，重启后必须重新扫码；高清格式与多视频稳定性尚未充分验证。
- 用户提供 [lapian-player](https://github.com/HappinessJo/lapian-player) 作为视频相关参考，并提供本地源码压缩包供检查。该项目使用 C++/Qt：二维码登录、B 站元数据和分 P 解析、DASH 清晰度及编码列表、WinHTTP 下载和本地缓存、Windows DPAPI 凭据保存均有独立模块。其下载任务主要服务于边下载边播放和逐帧查看，并不等于 MOWO 所需的“下载完成后成为正式视频资产”。

### lapian-player 源码检查结论

- `QrLogin`/`QrLoginController` 管理二维码生成、轮询、确认、过期和取消；`BiliAuth` 在展示已登录前校验会话；`CredentialStore` 用当前 Windows 用户的 DPAPI 加密保存登录凭据。
- `BiliResolver` 把 BV 链接解析为标题、作者、时长和分 P；`PlayUrl` 分析 `durl` 与 DASH 的视频、音频流；`QualityMenu` 根据实际返回的流列出清晰度与 AVC、HEVC、AV1 编码。
- `DownloadJob` 通过 Range 请求、断点续下、备用地址、重试与刷新过期地址写入缓存；`CacheStore` 管理 `.part` 和完成文件；`GrowingSource` 让播放器读取仍在增长的文件。这些是播放器的缓存系统，不宜整体移植到基于浏览器的 MOWO。
- 源码和文档对高清能力的验证有边界：账号、视频及编码会影响可选格式，不能把 4K 或 60fps 写成保证可用的能力。

### 候选方向，待用户确认

优先设计 MOWO 内的完整闭环：从现有“下载视频”入口粘贴 B 站链接，应用内扫码，解析标题、分 P 和账号可用的清晰度，选择后创建可恢复的下载任务；完成后预览并明确导入当前项目资产库。下载文件进入本地任务临时区，成功导入后由资产库管理，画布放置留到下一阶段。

`line` 的扫码交互和排障记录可作为参考，但不决定 MOWO 的选型。MOWO 使用自己的下载任务、素材入库与本地数据边界；下载实现优先评估成熟提取器与 FFmpeg，不把 B 站解析协议写进前端。登录凭据需要可由同一 Windows 用户在重启后恢复，并提供退出登录、失效重扫和错误提示。

本阶段需要确认的产品取舍：首批是否仅支持普通 B 站视频与指定分 P；清晰度由用户选择还是默认最高；成功下载后自动入库还是预览确认后入库；是否把登录状态跨重启保留列为首版必需。以上仍是候选方案，不属于正式需求。

## 2026-11-11：按 MOWO 架构重新评估技术方案

用户要求不以 `line` 的既有实现为选型前提。MOWO 目前是 Next.js/TypeScript + SQLite + 本地资产目录；LINE 下载任务虽已入库，但运行器保存在 Node 进程内，进程退出后的任务恢复还不足以直接承载长视频。现有 `download_tasks` 和 `download_items` 偏向 LINE 图片，不能只把平台枚举改成 B 站。

候选路线：

1. **自行用 TypeScript 实现 B 站解析与下载协议**：与主工程语言一致，但 B 站登录、签名、清晰度、分 P、DASH、过期地址和反爬变化都由 MOWO 长期维护，投入和回归风险最高。
2. **把 lapian-player 的 C++/Qt 下载模块移植过来**：登录与断点缓存设计可借鉴，但它围绕播放器的 WinHTTP、GrowingSource、缓存和逐帧解码组织；将其嵌入 Next.js 需要额外原生绑定或独立服务，边界不合适。
3. **独立下载工作进程使用成熟提取器，MOWO 负责产品流程**：首选评估 `yt-dlp` Python API + FFmpeg 的受控工作进程。主应用持有任务、凭据和资产身份；工作进程只做元数据提取、格式选择、下载与合并，通过结构化事件报告进度和错误。用户已认可这一职责划分；具体工具组合仍待技术验证。

推荐把扫码与凭据管理放在 MOWO 服务端，使用 Windows 当前用户加密存储；凭据只在启动工作进程时短暂交接，不写入任务记录、日志或画布。任务状态写 SQLite；进程重启时识别未完成任务并明确恢复或重试。下载先写任务临时目录，校验容器、音轨、尺寸和时长后才进入资产模块，保证半成品不出现在素材库。下载格式的实际可用性由账号与视频返回结果决定；浏览器不直接访问 B 站媒体 URL。

需要通过小型验证确认：受控工作进程的 Windows 打包方式、扫码凭据交接、高清格式枚举、分 P 选择、取消与重启恢复、不同编码的本地预览兼容性，以及 FFmpeg 分发许可与版本更新策略。验证后再把候选写成架构决策。

## 下载体验还需确认的产品问题

| 主题 | 推荐方向 | 待确认点 |
|---|---|---|
| 素材来源 | 首批聚焦普通 B 站视频与指定分 P，保留本地视频导入的同一资产入口 | 是否同时支持多 P 批量、合集、番剧；其他平台何时加入 |
| 登录 | 可匿名解析公开内容；需要账号权限时提示扫码。登录成功后展示状态，失效时可重扫 | 首版是否要求跨重启保持；是否允许多账号 |
| 选择下载 | 解析后先展示标题、封面、分 P、时长及实际可用的清晰度；默认推荐兼容画布预览的格式 | 用户是否可选编码、音轨；是否默认最高画质 |
| 资源预算 | 下载前给出可估计的大小和可用磁盘空间提示；大型任务控制并发 | 单视频、单任务和临时目录上限；低空间时如何暂停或终止 |
| 任务体验 | 任务可查看下载、合并、校验、待导入等阶段，允许取消、失败重试和重启后恢复 | 暂停/继续是否首版必需；关闭弹窗后任务是否继续 |
| 结果入库 | 成功校验后给出预览及导入操作；入库后在资产库保留来源与格式信息 | 自动入库还是确认入库；重复下载时复用还是另建记录 |
| 预览兼容 | 原画质文件与浏览器播放能力分开处理；不兼容时提供可播放预览方案 | 是否在首版生成兼容预览副本；占用空间如何告知 |
| 失败与边界 | 明确区分登录失效、权限不足、链接无效、平台限流、网络失败、磁盘不足、合并失败 | 用户能否保留已下载的部分数据以便继续 |

从 lapian-player 优先借鉴的是状态划分、会话校验、可用格式展示、重试与过期地址刷新、部分文件与正式文件隔离。`GrowingSource` 的边下载边播能力暂不作为下载阶段的前提；它是否适合后续逐帧查看，要以画布播放体验和性能验证决定。

## 视频拖入画布的大小分流：候选规则

用户再次确认：较大的视频从素材库拖上画布时，应提示是否进入独立视频编辑页。候选默认值为**原片时长超过 5 分钟，或原片文件超过 500 MiB**时提示；两者任一满足即提示，等于阈值时不提示。文件体积反映磁盘/传输负担，时长更直接反映分镜检测和拆帧的工作量。这个阈值是交互起点，需用真实素材和本机性能验证后再定稿。

提示只建议“进入视频编辑”或“仍放到画布”，不阻止用户放置视频，也不自动启动分镜任务。用户选择“仍放到画布”时创建视频节点；选择“进入视频编辑”时打开编辑页，原视频资产仍留在素材库。提示应以原片元数据判断，不以兼容预览文件的体积判断；缺少时长/大小时允许放置并显示信息不足，不猜测为大视频。未来可加“对此视频不再提示”偏好，首版不要求全局阈值设置。
